ترانه‌یار ۳.۱۷.۱۱ — رفعِ کوئریِ گرانِ صفحهٔ خانه
================================================================

این نسخه بالاخره **رفع** است، نه تشخیص. دو چیزِ گران پیدا شد و
هر دو رفع شدند. یک نگهبان هم اضافه شد که دیگر «لودینگ ابدی» ممکن نباشد.


ریشهٔ مشکل (اندازه‌گیری‌شده)
----------------------------------------------------------------
روی staging با ۵٬۵۰۰ آهنگ و ۳۵٬۹۳۴ ردیف متا، تکتک کوئری‌های
صفحهٔ خانه را زمان گرفتم:

  video OR/EXISTS (apex)           278ms   ← ۱۰ برابر بقیه
  vip LIKE + CALC_FOUND_ROWS        34ms
  album musics_type IN              18ms
  latest_releases (۳ کلید)          38ms
  mood get_terms                     8ms
  همهٔ کوئری‌های دیگر               زیر ۲۰ms

آن ۲۷۸ms روی SQLite بود. روی MySQL با جدولِ بزرگ‌تر و بدون
ایندکسِ ترکیبی، همین کوئری می‌تواند ده‌ها ثانیه شود — و
اندازه‌گیریِ پروداکشن (۳.۱۷.۸) نشان داد بخشِ apex ۷۹٬۵۱۶ms شد.


مشکل ۱ — meta_query با OR + EXISTS (بخش apex)
----------------------------------------------------------------
کدِ قبلی:

    'meta_query' => array(
        'relation' => 'OR',
        array( 'key' => 'video720',  'compare' => 'EXISTS' ),
        array( 'key' => 'video1080', 'compare' => 'EXISTS' ),
    )

MySQL برای این کوئری دو INNER JOIN روی postmeta می‌سازد و بعد
GROUP BY می‌زند تا ردیف‌های تکراری را جمع کند. این کار باعث
می‌شود حتی ایندکسِ (meta_key, post_id) هم بی‌فایده شود.

کدِ تازه: هر کلید **جدا** جست‌وجو می‌شود (یک شرط روی meta_key،
نه JOIN). اتحاد نتایج در PHP انجام می‌شود — دو آرایهٔ حداکثر ۸تایی.
ترتیب هم مثل قبل بر تاریخ نوشته است.

  نتیجه:  278ms → 136ms  (روی staging)
  محتوا:  همان ۸ کارت، همان ترتیب


مشکل ۲ — vip_slider
----------------------------------------------------------------
دو تغییر:

  ۱) no_found_rows روشن شد
     WordPress با SQL_CALC_FOUND_ROWS کلِ تطبیق‌ها را می‌شمرد
     در حالی که post_count هیچ‌جا استفاده نمی‌شد.

  ۲) compare از LIKE به '=' تغییر کرد
     مقدارِ ذخیره‌شده یا '1' است یا نیست. LIKE با الگوی '%1%'
     ایندکس را از کار می‌اندازد. (در wpdb درصدها escape می‌شوند،
     پس رفتار عملاً از قبل هم تساوی بود.)

  نتیجه:  61ms → 49ms روی staging، و روی MySQL تفاوت بزرگ‌تر است
          چون شمارشِ کلِ جدول حذف شده.


نگهبانِ زمانی (تازه)
----------------------------------------------------------------
حتی با این اصلاح‌ها، اگر سروری باز هم کند باشد، صفحه نباید بکشد.
حالا هر کوئریِ بخشِ خانه بودجه دارد:

  اگر از بودجه بگذرد:
    • همان بخش خالی برمی‌گردد (نه کل صفحه)
    • برای ۱۰ دقیقه آن بخش رد می‌شود (transient)
    • بقیهٔ صفحه سالم باز می‌شود

  بودجهٔ پیش‌فرض: ۲۵۰۰ms

  تغییرش:
    add_filter( 'tara_home_query_budget', fn() => 1500 ); // ms
    add_filter( 'tara_vip_budget',         fn() => 1500 );
  خاموشش:
    add_filter( 'tara_home_query_budget', '__return_zero' );

  تست شد: با بودجهٔ ۱ms بخش رد شد و بار دوم ۰.۰۰۰ms برگشت.


مقایسهٔ ۳.۱۵.۰ و ۳.۱۷.۱۱
----------------------------------------------------------------
  ۳.۱۵.۰:  apex وجود نداشت، vip_slider هیچ چاپ نمی‌کرد
  ۳.۱۶.۰:  هر دو اضافه شدند ← شروع مشکل
  ۳.۱۷.۱۱: همان هر دو، با کوئریِ سبک + نگهبان


اگر باز هم کند بود
----------------------------------------------------------------
۱) این را در wp-config.php بگذارید (قبل از «stop editing»):

       define( 'TARA_HOME_CACHE_TTL', 3600 );

   کش بخش‌ها از ۱۰ دقیقه به ۱ ساعت می‌رود. بازدیدکنندهٔ بعدی
   هیچ کوئری‌ای نمی‌زند.

۲) اگر خواستید بخش‌ها را کم کنید (هر کدام جدا):

       add_filter( 'tara_home_section', function( $on, $key ) {
           if ( 'home_sec_video' === $key ) { return false; }
           return $on;
       }, 10, 2 );

۳) ایندکسِ دیتابیس — اگر cPanel دارید، در phpMyAdmin:

       ALTER TABLE wp_postmeta
         ADD INDEX meta_key_post_id (meta_key, post_id);

   این برای هر meta_query کمک می‌کند، نه فقط این قالب.
   ⚠ اگر از قبل ایندکسِ مشابهی دارید، خطا می‌دهد — بی‌خطر است.


تغییرِ ظاهر: هیچ.
همان بخش‌ها، همان کارت‌ها، همان ترتیب. فقط سریع‌تر و با نگهبان.
